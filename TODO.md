### 2026-09-15 — In-app notifications (event-driven types only; push and the two time-based types still deferred)

First real piece of the long-deferred Notifications item — scoped down from the full ask ("checkout reminders and task overdue") to what doesn't need an unanswered timing question first: `task_assigned` and `leave_decided`/`leave_submitted`, both fired directly off a real DB event.

Schema (`supabase/0028_notifications.sql`): a generic `notifications` table, populated **only by SECURITY DEFINER database triggers**, never application code — same defense-in-depth reasoning as `employees_restrict_self_update`, so a future feature can never forget to insert a notification. Found and worked around the same class of RLS gotcha `ARCHITECTURE.md`'s avatar-upsert note already documents for a different table: a plain (non-SECURITY-DEFINER) trigger function runs as the *inserting user's own role* and gets rejected by RLS the same way a bare client-side insert into someone else's notifications would, since no insert policy exists for `authenticated` (deliberately — a client should never be able to create or destroy another user's notification directly). Also applied the "blanket UPDATE grant, RLS only restricts rows not columns" pattern from the same doc section: a `notifications_restrict_self_update` trigger blocks changing anything but `read_at`, so the "mark as read" update policy can't be used to rewrite a notification's own title/body.

Mobile UI: a bell icon with a live unread-count badge on every tab-root `AppHeader` (new `notifications` prop, pulls its own count the same way `accountMenu` pulls its own profile) plus a matching bell retrofitted onto the Check-In screen's bespoke header — that screen doesn't use `AppHeader` at all, but it's the single most-visited screen in the app, so it got the same treatment rather than being left out. Tapping opens a role-aware `/notifications` screen — reachable via the header, **not a 6th bottom tab**, matching this app's own existing "Schedule/Profile are header-reachable, not tab slots" precedent (see `(employee)/_layout.tsx`'s own comment on that). List is paginated the established `(offset, pageSize) -> { records, hasMore }` way; unread rows get a tinted background + dot; "mark all as read" lives in the screen's header action.

**Deliberately not built, and why**: push notifications (`expo-notifications`) — needs a real device to test, the exact same wall that's stalled verifying Phase 2 geofencing, so it's being held rather than shipped unverified. The two time-based types actually asked for (task-overdue, still-checked-in-past-expected-end) — both need a scheduled Supabase Edge Function + Cron (new infrastructure for this project, discussed but correctly identified as the non-trivial part) and both are still blocked on a real product decision (fire once or repeat? how much grace period?) that hasn't been made. ### 2026-09-15 — First real deploy of the admin web view; found and fixed two genuine static-export/hosting bugs

Direct user request to actually start the web view, after "we already have the logic, this will be just UI." Rather than assume that and start writing responsive-layout code, tested it first: `npx expo export -p web` succeeded with zero code changes, exporting all 46 routes (admin and employee alike) — a real, verified signal the shared logic genuinely is platform-agnostic, not just an assumption.

Deployed that export as-is via `vercel --prod` (no GitHub link — see below) to confirm it actually runs, before scoping down to admin-only or doing any real layout work. Two real bugs surfaced, both about how the static export is hosted, not the app's own code:

1. **Route-group URLs 404'd** (`/login`, `/tasks`, `/kpi`, etc.) — Expo Router's static export does emit a flat top-level `.html` for every route including ones under a route group like `(auth)`, but Vercel doesn't resolve extensionless URLs to `.html` files by default for an unrecognized static project. Fixed with a `vercel.json` `{"cleanUrls": true}`.
2. **Real blank-screen bug**: the root layout gates all rendering on `useFonts()` resolving (`if (!fontsLoaded) return null`) — and the Inter font files 404'd, so it never did. Root cause: Vercel silently excludes any path containing a literal `node_modules` folder from static deployments (a documented Vercel default, not a bug in this project) — and Expo's export happens to nest the Google Fonts package's `.ttf` files under `assets/node_modules/@expo-google-fonts/...`, mirroring its path in `node_modules`. Confirmed by testing: a different asset folder without `node_modules` in its path (`assets/assets/...`) served fine; the font path didn't. Fixed by renaming that folder to `assets/_vendor` and patching the 49 matching path references inside the built JS bundle (`entry-*.js`) to match — a plain string replace, safe since bundled paths are string literals, not something Metro needs to re-resolve at this point.

**Why this mattered to catch now rather than later**: both bugs are invisible to `curl` (they're either "the JS never executed" or "a resource the JS wants 404s at runtime") — confirmed the user's own browser console before diagnosing further, rather than guessing from server-side checks alone, same discipline as live-testing the mobile app on the emulator rather than trusting `tsc --noEmit`.

**Genuine limitation, not yet solved**: this deploy is a manual snapshot, not CI-linked. `dist/` is gitignored (correctly — it's a build artifact) and the Vercel project's GitHub auto-connect failed the same way `attendance-download`'s did. Any future app code change needs a human (or Claude) to re-run `expo export -p web` → rename `assets/node_modules` → `assets/_vendor` and patch the bundle → `vercel --prod` from `dist/`, by hand, every time. ### 2026-09-04 — Real Android bug: date/time pickers crashed on cancel ("Cannot read property 'dismiss' of undefined")

### 2026-09-03 — Two real bugs found via live testing against the real Supabase project, fixed

With `0001_initial_schema.sql` applied and real credentials in `.env.local`, a direct REST check against the live project (not assumed) surfaced two real issues:

1. **`permission denied for table employees` (42501) on every table**, even though RLS policies were correct. Cause: Postgres requires base table-level `GRANT`s to the `anon`/`authenticated` roles before RLS is even evaluated, and this project didn't have Supabase's usual default privileges bootstrapped onto the tables `0001` created. The original design had the client insert its own `employees` row immediately after `auth.signUp()`, which only works if signUp() returns an active session right away — with confirmation on, it doesn't, so that insert would run unauthenticated and fail. Fixed properly (not patched around) with the standard Supabase pattern: `supabase/0003_auto_create_employee_profile.sql` adds a security-definer trigger on `auth.users` that creates the matching `employees` row at signup time regardless of confirmation state, and drops the now-unnecessary client-writable insert policy on `employees` (tightens security — zero client-writable insert path into that table now). `authService.signUp()` no longer inserts a profile itself; it passes `name` via signup metadata for the trigger to read, and returns `needsEmailConfirmation` so `RegisterScreen` can show a real "check your email" state instead of silently doing nothing.

**Why**: found by actually testing against the live project instead of assuming the schema/auth design was correct — exactly the "verify real behavior, don't assume" habit from `RULES.md`, just applied to backend/auth instead of device behavior.
