# Attendance App — Project Context for Claude

## Tech Stack
- **Expo (React Native)** — mobile app, iOS + Android (+ web, since Expo supports it, but not the priority target unless stated otherwise).
- **Supabase** — backend (Postgres + Auth + Realtime). **Resolved (2026-09-03): its own separate Supabase project**, not the CRM's — own roster, own schema, no shared source of truth. The client talks to Supabase directly (no server/API layer like the CRM's Vercel routes), so Postgres RLS is real and load-bearing here, not the CRM's current policy-free "soft" RLS — see `supabase/0001_initial_schema.sql`.
- Sibling project to `../crm` (a real internal CRM for the same business) — this app tracks attendance/tasks/KPIs for the same real staff the CRM's Employee module already models, but is its own separate app/codebase with its own copy of the roster (see Roles below).
- **Distribution (resolved 2026-09-03)**: internal only, no Google Play / App Store listing planned. Android installs via a direct link/QR code (EAS's built-in internal distribution — see `ARCHITECTURE.md`'s Distribution section). iOS has no equivalent raw-sideload path — needs TestFlight at minimum.

## Core Concept
A real internal mobile app for a business's staff to check in/out of work, request time off, receive tasks with deadlines from admins, and have their performance tracked (KPI) based on task completion. Not a public product — internal tool, same spirit as the CRM.

## Core Features (as described so far, real requirements not invented)

1. **Attendance (check-in/check-out)**
   - Staff check in via the app when they arrive at work.
   - **Proximity-based auto-checkout**: once checked in, if the employee physically leaves the company's location without manually checking out first, the app automatically checks them out and records that time on their attendance record — no admin action needed to trigger it.
   - **Resolved (2026-09-03)**: a fixed location (lat/lng, stored in `locations`) per employee, with a **4km radius** default (editable per location) — leaving that radius while checked in triggers the auto-checkout.
   - **Phase 2 — background geofencing (code-complete 2026-09-03, NOT yet verified on a real device)**: `expo-location` region monitoring + an `expo-task-manager` background task (`features/attendance/services/geofenceTask.ts`) auto-checks-out an employee on exiting their assigned location's radius, tagged `check_out_type: 'auto_geofence'`. Requires "Always" location permission — a separate, more invasive ask than the foreground permission, requested only after check-in (not upfront) with its own explainer, and entirely optional: declining just means manual checkout keeps working exactly as before. Needs `expo-dev-client` + an EAS/local dev build to run at all — cannot run in Expo Go, and cannot be verified by Claude in this environment (no simulator/device, and background execution fundamentally doesn't exist in a web browser). Verified so far: type-checks; the background task's registration (`TaskManager.defineTask`, called unconditionally at app boot per Expo's documented pattern) doesn't crash the web build; normal foreground check-in/out is unaffected. **Not verified**: that an exit event actually fires and auto-checks-out on a real device — that requires the real-device test described in `TODO.md`.
   - **Foreground location permission is a hard gate on checking in (resolved 2026-09-13)**: an employee who hasn't granted foreground location can't check in at all — a non-dismissable modal blocks the whole screen (not just an ignorable inline card) explaining why, with a single action that's either "Allow location access" (re-prompts the OS dialog) or "Open Settings" (once the OS has hard-denied and won't prompt again, per `canAskAgain`). Enforced at the hook level too (`useAttendance`'s `performCheckIn` itself refuses without granted permission), not just the screen's UI. Deliberately scoped to checking IN only — someone already checked in, or whose permission got revoked mid-shift, can still check out freely, unaffected by this gate.
   - **"Roaming employee" flag (added 2026-09-14)**: an admin-toggleable per-employee setting (`employees.is_roaming`, Staff Profile's Profile tab) for staff who legitimately work across multiple locations (e.g. a technician sent to another branch). Check-in itself has never been location-restricted — this flag specifically skips arming Phase 2's background auto-checkout geofence for that employee, so leaving their *assigned* location's radius doesn't incorrectly auto-check them out. Everything else about their attendance (check-in/out, late/early flagging against their assigned location's expected hours) is unaffected.
   - **Employee deactivate (added 2026-09-15)**: an "Active employee" toggle on Staff Profile (`employees.active`, which existed since day one but nothing ever set it). Off genuinely blocks check-in — enforced at the RLS level (`attendance_insert_own`, `supabase/0026_attendance_insert_requires_active.sql`), not just the UI, so a direct API call can't bypass it either. The employee's own Check-In screen shows an "Account inactive" explainer and disables the swipe control. The Staff roster defaults to an "Active" filter (departed staff hidden by default, one tap away via "All"), matching Leave's own "defaults to Pending" reasoning.
   - **Half day (resolved 2026-09-03)**: self-declared by the employee — a Full day/Half day toggle shown at check-in time, saved on that day's attendance record. Not auto-computed from hours worked (rejected — needs a threshold and can misclassify a legitimately short day).
   - **Employee attendance history (added 2026-09-03)**: employees can see their own time-in/time-out per day (grouped by date, with duration and a Half day/Auto-out indicator) — a dedicated "Attendance" tab, not folded into the check-in screen.
   - **Weekly timesheet grid (added 2026-09-04)**: a Monday–Sunday grid at the top of the Attendance tab, above the day-by-day list — today's column highlighted, each day showing total hours worked, with prev/next week navigation. Inspired by Deputy/Homebase's timesheet pattern, found while researching modern attendance-app UI/UX.
   - **Admin per-employee history (added 2026-09-04)**: an admin viewing a specific employee's profile (Staff roster → tap an employee) sees that employee's full task list *and* their attendance history (check-in/out times, duration, Half day/Late/Left early flags, Auto out/Admin correction) together on one screen, so there's no need to cross-reference two separate admin tabs to understand one employee's activity.
   - **Human-readable check-in/out location (added 2026-09-03)**: coordinates are reverse-geocoded into an address on-device (`expo-location`, no API key) and stored alongside the raw lat/lng — best-effort, since geocoding is unsupported on web and can fail even on-device, so this never blocks a check-in/out. A "View on map" action opens it in the device's Maps app via a URL scheme, deliberately not a full map-SDK dependency (`react-native-maps` would need native config/a dev client, same constraint as Phase 2 geofencing).
   - **Late arrival / early departure (added 2026-09-03, now per-location)**: flagged at check-in/out against the employee's *assigned location's* expected hours (`locations.expected_start`/`expected_end`, editable on the Locations screen, defaults 09:00–18:00). Falls back to the global `src/constants/workHours.ts` default only for an employee with no location assigned yet.
   - **Locations management (added 2026-09-03)**: admins can create/edit a `locations` row (name, latitude/longitude, geofence radius — defaults to 4km — and expected work hours, see above) from a screen reached off the Staff roster, with a "Use my current location" button (reuses the existing check-in geolocation code) instead of an interactive map picker, deliberately avoiding a map-SDK dependency. Admins assign an employee to a location from that employee's profile. This is the real prerequisite for Phase 2 geofencing (nothing to geofence against without it) — found RLS on `locations` had been enabled since day one with zero policies (deny-all) while building this; fixed as part of the same change (`supabase/0009_locations_management.sql`).
   - **Delete (added 2026-09-11)**: admins can also delete a location, with a confirmation dialog — needed a real migration (`supabase/0018_locations_delete_policy.sql`), unlike edit which already worked. Deleting a location still assigned to any employee fails with a real foreign-key error rather than silently unassigning them; the dialog says so upfront.
   - **CSV export for payroll (added 2026-09-04)**: admins export attendance history as a CSV from the Staff Attendance screen's "Recent history" tab, shared via the OS share sheet (Drive, email, Files) — there's no "download" concept on mobile. First feature to need `expo-file-system`/`expo-sharing`, so it needed a real native rebuild, not just a JS reload. **Scoped to an admin-picked date range (changed 2026-09-14)**: originally fetched the entire table unconditionally; now defaults to first-of-this-month through today (a real payroll period) with From/To date pickers, and the shared filename includes the range.
   - **Recent history filtering + scale (added 2026-09-14)**: "Recent history" has a `Filters` button (`AppFilterButton`/`AppFilterSheet`, see `AGENTS.md`) for Late/Left early/Half day/Auto checkout, combined server-side with OR since the list is paginated — the same button+sheet pattern used app-wide on Tasks and Leave too, not a one-off. A real index (`attendance_check_in_at_idx`, `supabase/0022_attendance_indexes.sql`) now backs the `check_in_at` ordering every attendance list query uses, added after the user flagged that an ever-growing, unindexed history would become a real fetching problem. Not yet decided: whether "Recent history" itself should default to a bounded period (e.g. "this month" with navigation) instead of open-ended infinite scroll.
   - **Admin edit and delete of an attendance record (edit added 2026-09-14, delete 2026-09-15)**: tapping a record (from Recent history, Checked-in, or a Staff Profile's attendance section) opens a detail screen that, for an admin viewer only, has Edit and Delete actions. Edit: check-in time, day type, and Late/Left-early can be corrected; check-out time is editable only on an already-closed record (an open one is still closed via the existing checkout action, not this form). Delete permanently removes a stray/duplicate record, with a confirmation dialog. Fixes the two highest-impact gaps from the 2026-09-11 CRUD-gap audit: previously a written attendance record was both un-editable and un-deletable. RLS: edit reused the existing `attendance_update_admin` (0005); delete needed a new admin-only policy (`supabase/0025_attendance_delete_policy.sql`, since no delete grant/policy existed on this table at all).

2. **Weekly schedule (added 2026-09-04)**
   - Employees can declare the days/hours they normally work — a recurring Monday-first weekly pattern (day off, or a start/end time), self-service, no admin approval. Reached from a "My schedule" row at the top of the Attendance tab, not a separate bottom tab.
   - Deliberately **not** where day-offs, sick leave, or vacation live — that's the Leave feature below, which already has a real approval flow. Schedule is purely "what's normal," informational only.
   - Admin can view (read-only) an employee's schedule from their Staff Profile, alongside that employee's tasks and attendance history — same "see everything in one place" reasoning as the admin per-employee history below.

3. **Leave / time-off requests (added 2026-09-03)**
   - Employee requests a date range off (vacation/sick/emergency/other) with an optional reason; admin approves or rejects. Employee can withdraw their own pending (or already-approved) request; only an admin can approve/reject. Genuinely separate from daily check-in/out — this is planned, in-advance absence, not something declared at check-in.
   - **Leave balance (added 2026-09-04)**: each employee has an annual vacation-day allotment (`employees.annual_leave_days`, default 15, admin-editable), shown as "`N` days left this year" on the employee's Leave tab. Only `vacation`-type approved requests count against it — sick/emergency/other stay unlimited. Informational only; exceeding the balance doesn't block a request (no policy decided for that yet).
   - **Admin filtering (added 2026-09-10)**: the admin's Leave tab filters by status (All/Pending/Approved/Rejected/Cancelled) and **defaults to Pending**, not All — a deliberate choice, since this screen's actual job is reviewing what needs a decision, and mixing in years of already-decided requests worked against that.
   - **Optional photo + location evidence (added 2026-09-12)**: a request can optionally carry a photo (`leave_requests.attachment_path`, a private Storage bucket — unlike the public `avatars` bucket, since a leave attachment can be more sensitive) and/or the employee's current location at submission time, e.g. proof for a weather-related lateness/absence request. Neither is required — most requests (planned vacation, routine sick leave) need neither. Viewing an attachment uses a short-lived signed URL, not a public link; the reviewing admin or the employee who submitted it are the only ones who can generate one (RLS on `storage.objects`, `supabase/0020_leave_request_attachments.sql`).
   - **Edit and hard delete (added 2026-09-15)**: an employee can now edit any field on their own still-pending request in place (same form as creating one) instead of cancel + resubmit as two separate requests. Both employees and admins can now permanently delete a request — an employee only while it's pending or cancelled (a decided approved/rejected request stays as a record even for the employee who filed it, so there's still an audit trail); an admin can delete any. RLS: `supabase/0027_leave_requests_edit_delete.sql`.

4. **Task assignment**
   - Admins can give an employee a task with a deadline.
   - Employees see their assigned tasks. **Resolved (2026-09-03)** — fields: assignee, assigner, task name, description, created date/time, deadline (date + time), **priority** (low/medium/high, added 2026-09-03). Status model (a reasonable default, not explicitly specified): `assigned → in_progress → done`, with `overdue` computed client-side from deadline vs. now rather than stored, to avoid needing a background job for v1.
   - **UX flow (resolved 2026-09-03)**: no standalone "assign task" form with an employee picker — an admin taps into a specific employee's profile (from the Staff roster) and assigns the task from there, so the assignee is implicit from context. The Tasks tab is a read-only overview across everyone (filterable by status — All/Overdue/Assigned/In progress/Done — since 2026-09-10, overdue sorted first).
   - **Editing and deletion (added 2026-09-10)**: a task can be corrected (title/description/deadline/priority) or deleted after creation, from the same employee-profile screen it was assigned from — previously the only way to change a task at all was advancing its status. RLS already allowed both (`0001`'s `tasks_update_assignee_or_admin`/`tasks_delete_admin_only`), unused until this was actually built.
   - **Status can move backward (added 2026-09-15)**: the status control is a direct 3-way Assigned/In progress/Done picker, not a forward-only "advance" button — a task marked done by mistake can be reopened in one tap. Needed zero RLS change; `tasks_update_assignee_or_admin` already allowed setting any status, the forward-only behavior was purely a client-side restriction.

5. **KPI / performance tracking**
   - Derived from task completion (presumably: on-time completion rate, task volume, or similar — the exact formula is not yet decided, see Open Questions). **Explicitly deferred by the user until other features are working** — no schema or calculation exists yet, just a stub screen.
   - Displayed per-employee, likely on "their page" (their own profile/dashboard, and probably an admin-facing view too, though not yet confirmed).

6. **Company holidays (added 2026-09-14)**
   - Admins manage a `holidays` list (name + specific date) from a "Holidays" shortcut on the Staff tab's header, next to "Locations." One-off dates deliberately, not a recurring yearly rule — several real holidays (Eid al-Fitr, Eid al-Adha, Lunar New Year) move every year against the Gregorian calendar, so a fixed month/day rule would be wrong for them; an admin re-enters each year's dates instead. Company-wide, not per-location. Built ahead of any actual behavior change (no late-flag suppression, no dashboard integration yet) as prep work for the future admin web view — the real data/API layer exists now so that later work is a UI experiment on a stable backend, not a reason to build the backend and frontend together.

7. **In-app notifications (added 2026-09-15)**
   - A generic `notifications` table (`supabase/0028_notifications.sql`) — one row per recipient per event, `type` discriminator, `related_id` for deep-linking, `read_at` nullable — populated **only by database triggers, never application code**, so a future feature can never forget to notify. Two event-driven types ship now, both firing off a real DB event with no open question attached: `task_assigned` (notifies the assignee the moment a task is inserted) and `leave_decided`/`leave_submitted` (notifies the employee when their request is approved/rejected, and every admin/super admin the moment a new request comes in — so there's a real record on the reviewing side too, not just the employee side). A bell icon with a live unread-count badge sits on every tab-root header (`AppHeader`'s new `notifications` prop) and on the Check-In screen's own custom header (the single most-visited screen in the app, deliberately not left out just because it doesn't use `AppHeader`) — tapping opens a role-aware Notifications screen (`/(employee)/notifications`, `/(admin)/notifications`), not a 6th bottom tab (the same "reachable via header, not a tab slot" precedent this app already set for Schedule/Profile).
   - **Deliberately not built yet**: push notifications (`expo-notifications` — needs a real device to test, can't be verified in this environment, same wall that's stalled geofencing verification) and the two time-based types this was originally asked for, task-overdue and still-checked-in-past-expected-end — both need a scheduled Supabase Edge Function + Cron, and both are still blocked on deciding the actual trigger rule (fire once or repeat? how much of a grace period?), the same "explicitly deferred, brainstorm later" state Notifications has been in since day one, just narrowed now to specifically these two. The schema is intentionally generic enough that adding them later is a new trigger/scheduled job, not a schema change.

8. **Admin dashboard (added 2026-09-04)**
   - The admin's Staff tab (the true landing screen) opens on a **"Dashboard" tab** with five stat cards — checked in now, late today, on leave today, pending leave requests, overdue tasks — each tapping through to the relevant tab. A separate **"Staff (`N`)" tab** holds the roster list itself — real tabs, not one continuous scroll, matching the same split already used on the Attendance screen (Checked-in / Recent history). Added after researching real competitors (Homebase, Deputy, When I Work, Connecteam) specifically to find *genuine* gaps rather than re-skinning what already matches the category's best-regarded patterns (this app's Check-In screen already had the big-button/GPS-confirmed/card-based look Homebase is praised for).
   - **Staff roster search (added 2026-09-10)**: the Staff tab's roster list is searchable by name, position, or department.

## Profile pictures (added 2026-09-04)

Employees self-service upload their own profile photo (not admin-managed) — shown wherever their identity appears (Staff roster, Staff Attendance rows, Staff Profile, their own Check-In greeting), falling back to initials when none is set. Confirmed with the user this doesn't trigger any KYC/compliance obligation — KYC is a financial-services identity-verification framework tied to regulated money handling, unrelated to a basic profile photo on an internal attendance tool. Stored in a public Supabase Storage bucket (`avatars`) — public read since a profile photo is meant to be seen and is low-sensitivity, unlike attendance coordinates or leave reasons; writes stay fully locked to the account owner. See `ARCHITECTURE.md`'s note on `AppAvatar` and the RLS trigger this needed.

**Removable, and a real "My Profile" screen (added 2026-09-11)**: an employee can remove their photo (reverts to initials) as well as replace it, and can now also edit their own display name — both from a new `MyProfileScreen`, reached by tapping their identity on the Check-In screen or "View profile" in the account menu on any tab-root header. Every other profile field (email, position, department, mobile number) stays admin-only, shown read-only with a note to contact an admin.

## Employee profile editing (added 2026-09-10)

Admins can edit an employee's name, position, department, and mobile number from that employee's Staff Profile screen — previously nothing but `location_id` was editable anywhere in the app. Deliberately **not** email: that column just mirrors `auth.users.email`, set once at signup; editing it here alone would desync the two (the employee's real login email wouldn't change, so they'd keep signing in with the old address while the app showed a different one). A real email-change flow needs Supabase Auth's own admin API — not built, not needed yet. RLS already permitted this (admins can already update any column on any employee row, `0001`'s `employees_update_admin_only`) — no schema change, just the missing UI.

## Account security (added 2026-09-16)

**Forgot password**: `LoginScreen` links to a new `ForgotPasswordScreen` (`(auth)/forgot-password`) that calls Supabase Auth's built-in `resetPasswordForEmail` — no new credentials, uses the same anon key already in the app. The reset email links to a page on **`attendance-admin`** (`/reset-password`), not back into this app — a mobile app can't be the direct target of an email link without deep-link handling this project doesn't have, and `attendance-admin` already talks to the same Supabase project. That page is deliberately outside `attendance-admin`'s `RequireAdmin` guard (any employee can land there, not just admins) and signs the recovery session out again once the password's updated, since it only ever existed for this one purpose. `attendance-admin` also has its own "Forgot password?" link on its own login screen, for admins who forget their web password independently — both flows share the same destination page. **Requires a manual, one-time step**: the reset URL (`<attendance-admin's deployed URL>/reset-password`) must be added to Supabase's Auth → URL Configuration → Redirect URLs allow-list in the dashboard, or Supabase silently falls back to the default Site URL instead of redirecting there. Also needs `EXPO_PUBLIC_ADMIN_WEB_URL` set in both `.env.local` and EAS's Environment Variables (same pattern as the Supabase URL/key).

**Biometric app lock**: an opt-in toggle on `MyProfileScreen` ("Require Face ID / fingerprint") — only shown on devices with biometric hardware enrolled (`expo-local-authentication`'s `hasHardwareAsync`/`isEnrolledAsync`). Device-level preference (`AsyncStorage`, not tied to which employee is signed in — this app already assumes one person per device, same assumption self-registration makes), enforced by `components/BiometricGate.tsx` wrapping the whole app above `AuthProvider`. Deliberately **not** session-dependent — it locks even the login screen itself on every cold start when enabled, the same way a personal "app lock" feature behaves, rather than trying to race session-loading to decide whether locking is needed. Turning the toggle on immediately triggers a real biometric prompt to verify it actually works on this device before the preference is saved, so enabling it can't lock someone out on their very next open. **Re-locks on returning from the background too (added 2026-09-16)**, not just a fresh cold start — an `AppState` listener in `useBiometricLock` tracks how long the app was backgrounded and re-locks past a 30s grace period, so switching away and back quickly (a notification, another app) doesn't force a fresh prompt every time, but leaving it backgrounded for real does.

**Haptic feedback (added 2026-09-16)**: a success buzz (`expo-haptics`) on check-in, check-out, and marking a task done — the physical confirmation on top of the visual one, easy to miss otherwise if attention's already drifted from the screen mid-action. Guarded to skip on web (`Platform.OS !== 'web'`), same as every other native-only call in this codebase.

## Roles (resolved 2026-09-03)
Three app roles: **Employee**, **Admin**, **Super Admin** — simpler than the CRM's 5-role system (`superAdmin`/`admin`/`branchManager`/`pageManager`/`serviceAdvisor`), since this app has no branch/page-manager/service-advisor edit-scoping to replicate. Super Admin is a strict superset of Admin (same pattern as the CRM's own `canEditLead`/`canDelete` in `../crm/src/domain/permissions.ts`) — no separate Super-Admin-only screens exist yet, since nothing Super-Admin-specific has been asked for. Employee *profile* fields (`position`, `department`) are modeled on the CRM's real `employees` table shape (checked directly in `../crm/supabase/wave_2_schema.sql`), since this app tracks the same real staff — but it's this app's own table in its own Supabase project (see Tech Stack), not a live join to the CRM's.

## Visual Design (resolved 2026-09-04, refined same day)

Airbnb-inspired, on explicit request: their real, publicly documented brand color ("Rausch" coral, `#FF385C`) as the accent, warm neutral surfaces (white/near-white, not cool gray), soft shadow-based cards instead of hard-outlined ones, generous whitespace, and — the part that most directly serves readability, not just looks — their actual text-color pairing (`#222222` primary text / `#717171` secondary text on white), a genuinely well-tested accessible combination, not just borrowed for aesthetics. Typography is **Inter** (not Airbnb's proprietary "Cereal", which can't be legally used) — the open alternative closest in spirit, and specifically designed for screen legibility at UI sizes (same reason GitHub/Figma/Linear use it). See `ARCHITECTURE.md`'s Theming section for the implementation.

**Refined same day** after the first pass "looked quite odd" in practice: bold/semibold had been used for nearly every text role, flattening hierarchy — bold is now reserved for real page-level titles (display/headline) only, everything else is medium at most. Also separated colors by *role*, not just palette: `statusColors.danger` moved off a coral-adjacent red (`#B3261E` now) so a "High priority" flag never reads as the same color as a real coral CTA, static avatars use `secondaryContainer` (teal) instead of `primary` so they don't look like buttons, and buttons that only *display* data (a deadline, an assigned location, a date picker) use neutral `onSurface` text instead of Paper's outlined-button default of `primary`. See `ARCHITECTURE.md`'s Theming section, "Color roles, not just a palette."

**"Warm... not cool gray" actually implemented (2026-09-11)**: the app's background had stayed a stark `#FFFFFF` since day one, despite this section's own stated intent — found while the user was independently describing the header as "bland." Now a warm `#FFFDF9`; cards stay pure white on purpose, so they read as sitting above the warm canvas. Tab-root headers (`mode="medium"` — downsized from `mode="large"`, see `ARCHITECTURE.md`'s Theming section) also got a soft coral wash instead of the plain background, and the sign-out icon on those headers became an avatar + account menu (View profile/Sign out) with a real confirmation step — previously a single tap signed the user out instantly, on every tab-root screen and the Check-In screen alike.
