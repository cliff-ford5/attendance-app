# Attendance App — Project Context for Claude

## Tech Stack
- **Expo (React Native)** — mobile app, iOS + Android (+ web, since Expo supports it, but not the priority target unless stated otherwise).
- **Supabase** — backend (Postgres + Auth + Realtime). **Resolved (2026-09-03): its own separate Supabase project**, not the CRM's — own roster, own schema, no shared source of truth. The client talks to Supabase directly (no server/API layer like the CRM's Vercel routes), so Postgres RLS is real and load-bearing here, not the CRM's current policy-free "soft" RLS — see `supabase/0001_initial_schema.sql`.
- Sibling project to `../crm` (a real internal CRM for the same business) — this app tracks attendance/tasks/KPIs for the same real staff the CRM's Employee module already models, but is its own separate app/codebase with its own copy of the roster (see Roles below).
- **Distribution (resolved 2026-09-03)**: internal only, no Google Play / App Store listing planned. Android installs via a direct link/QR code (EAS's built-in internal distribution — see `ARCHITECTURE.md`'s Distribution section). iOS has no equivalent raw-sideload path — needs TestFlight at minimum.

## Core Concept
A real internal mobile app for a business's staff to check in/out of work, request time off, receive tasks with deadlines from admins, and have their performance tracked (KPI) based on task completion. Not a public product — internal tool, same spirit as the CRM.

## Core Features (as described so far, real requirements not invented)

1. **Attendance (check-in/check-out)**
   - Staff check in via the app when they arrive at work.
   - **Proximity-based auto-checkout**: once checked in, if the employee physically leaves the company's location without manually checking out first, the app automatically checks them out and records that time on their attendance record — no admin action needed to trigger it.
   - **Resolved (2026-09-03)**: a fixed location (lat/lng, stored in `locations`) per employee, with a **4km radius** default (editable per location) — leaving that radius while checked in triggers the auto-checkout.
   - **Phase 2 — background geofencing (code-complete 2026-09-03, NOT yet verified on a real device)**: `expo-location` region monitoring + an `expo-task-manager` background task (`features/attendance/services/geofenceTask.ts`) auto-checks-out an employee on exiting their assigned location's radius, tagged `check_out_type: 'auto_geofence'`. Requires "Always" location permission — a separate, more invasive ask than the foreground permission, requested only after check-in (not upfront) with its own explainer, and entirely optional: declining just means manual checkout keeps working exactly as before. Needs `expo-dev-client` + an EAS/local dev build to run at all — cannot run in Expo Go, and cannot be verified by Claude in this environment (no simulator/device, and background execution fundamentally doesn't exist in a web browser). Verified so far: type-checks; the background task's registration (`TaskManager.defineTask`, called unconditionally at app boot per Expo's documented pattern) doesn't crash the web build; normal foreground check-in/out is unaffected. **Not verified**: that an exit event actually fires and auto-checks-out on a real device — that requires the real-device test described in `TODO.md`. Still open: exact UX on location-permission denial (separate from this — that's about the foreground prompt).
   - **Half day (resolved 2026-09-03)**: self-declared by the employee — a Full day/Half day toggle shown at check-in time, saved on that day's attendance record. Not auto-computed from hours worked (rejected — needs a threshold and can misclassify a legitimately short day).
   - **Employee attendance history (added 2026-09-03)**: employees can see their own time-in/time-out per day (grouped by date, with duration and a Half day/Auto-out indicator) — a dedicated "Attendance" tab, not folded into the check-in screen.
   - **Weekly timesheet grid (added 2026-09-04)**: a Monday–Sunday grid at the top of the Attendance tab, above the day-by-day list — today's column highlighted, each day showing total hours worked, with prev/next week navigation. Inspired by Deputy/Homebase's timesheet pattern, found while researching modern attendance-app UI/UX.
   - **Admin per-employee history (added 2026-09-04)**: an admin viewing a specific employee's profile (Staff roster → tap an employee) sees that employee's full task list *and* their attendance history (check-in/out times, duration, Half day/Late/Left early flags, Auto out/Admin correction) together on one screen, so there's no need to cross-reference two separate admin tabs to understand one employee's activity.
   - **Human-readable check-in/out location (added 2026-09-03)**: coordinates are reverse-geocoded into an address on-device (`expo-location`, no API key) and stored alongside the raw lat/lng — best-effort, since geocoding is unsupported on web and can fail even on-device, so this never blocks a check-in/out. A "View on map" action opens it in the device's Maps app via a URL scheme, deliberately not a full map-SDK dependency (`react-native-maps` would need native config/a dev client, same constraint as Phase 2 geofencing).
   - **Late arrival / early departure (added 2026-09-03, now per-location)**: flagged at check-in/out against the employee's *assigned location's* expected hours (`locations.expected_start`/`expected_end`, editable on the Locations screen, defaults 09:00–18:00). Falls back to the global `src/constants/workHours.ts` default only for an employee with no location assigned yet.
   - **Locations management (added 2026-09-03)**: admins can create/edit a `locations` row (name, latitude/longitude, geofence radius — defaults to 4km — and expected work hours, see above) from a screen reached off the Staff roster, with a "Use my current location" button (reuses the existing check-in geolocation code) instead of an interactive map picker, deliberately avoiding a map-SDK dependency. Admins assign an employee to a location from that employee's profile. This is the real prerequisite for Phase 2 geofencing (nothing to geofence against without it) — found RLS on `locations` had been enabled since day one with zero policies (deny-all) while building this; fixed as part of the same change (`supabase/0009_locations_management.sql`).
   - **CSV export for payroll (added 2026-09-04)**: admins can export the full attendance history (not just the on-screen recent list) as a CSV from the Staff Attendance screen, shared via the OS share sheet (Drive, email, Files) — there's no "download" concept on mobile. First feature to need `expo-file-system`/`expo-sharing`, so it needed a real native rebuild, not just a JS reload.

2. **Weekly schedule (added 2026-09-04)**
   - Employees can declare the days/hours they normally work — a recurring Monday-first weekly pattern (day off, or a start/end time), self-service, no admin approval. Reached from a "My schedule" row at the top of the Attendance tab, not a separate bottom tab.
   - Deliberately **not** where day-offs, sick leave, or vacation live — that's the Leave feature below, which already has a real approval flow. Schedule is purely "what's normal," informational only.
   - Admin can view (read-only) an employee's schedule from their Staff Profile, alongside that employee's tasks and attendance history — same "see everything in one place" reasoning as the admin per-employee history below.

3. **Leave / time-off requests (added 2026-09-03)**
   - Employee requests a date range off (vacation/sick/emergency/other) with an optional reason; admin approves or rejects. Employee can withdraw their own pending (or already-approved) request; only an admin can approve/reject. Genuinely separate from daily check-in/out — this is planned, in-advance absence, not something declared at check-in.
   - **Leave balance (added 2026-09-04)**: each employee has an annual vacation-day allotment (`employees.annual_leave_days`, default 15, admin-editable), shown as "`N` days left this year" on the employee's Leave tab. Only `vacation`-type approved requests count against it — sick/emergency/other stay unlimited. Informational only; exceeding the balance doesn't block a request (no policy decided for that yet).
   - **Admin filtering (added 2026-09-10)**: the admin's Leave tab filters by status (All/Pending/Approved/Rejected/Cancelled) and **defaults to Pending**, not All — a deliberate choice, since this screen's actual job is reviewing what needs a decision, and mixing in years of already-decided requests worked against that.

4. **Task assignment**
   - Admins can give an employee a task with a deadline.
   - Employees see their assigned tasks. **Resolved (2026-09-03)** — fields: assignee, assigner, task name, description, created date/time, deadline (date + time), **priority** (low/medium/high, added 2026-09-03). Status model (a reasonable default, not explicitly specified): `assigned → in_progress → done`, with `overdue` computed client-side from deadline vs. now rather than stored, to avoid needing a background job for v1.
   - **UX flow (resolved 2026-09-03)**: no standalone "assign task" form with an employee picker — an admin taps into a specific employee's profile (from the Staff roster) and assigns the task from there, so the assignee is implicit from context. The Tasks tab is a read-only overview across everyone (filterable by status — All/Overdue/Assigned/In progress/Done — since 2026-09-10, overdue sorted first).
   - **Editing and deletion (added 2026-09-10)**: a task can be corrected (title/description/deadline/priority) or deleted after creation, from the same employee-profile screen it was assigned from — previously the only way to change a task at all was advancing its status. RLS already allowed both (`0001`'s `tasks_update_assignee_or_admin`/`tasks_delete_admin_only`), unused until this was actually built.

5. **KPI / performance tracking**
   - Derived from task completion (presumably: on-time completion rate, task volume, or similar — the exact formula is not yet decided, see Open Questions). **Explicitly deferred by the user until other features are working** — no schema or calculation exists yet, just a stub screen.
   - Displayed per-employee, likely on "their page" (their own profile/dashboard, and probably an admin-facing view too, though not yet confirmed).

6. **Admin dashboard (added 2026-09-04)**
   - The admin's Staff tab (the true landing screen) opens on a **"Dashboard" tab** with five stat cards — checked in now, late today, on leave today, pending leave requests, overdue tasks — each tapping through to the relevant tab. A separate **"Staff (`N`)" tab** holds the roster list itself — real tabs, not one continuous scroll, matching the same split already used on the Attendance screen (Checked-in / Recent history). Added after researching real competitors (Homebase, Deputy, When I Work, Connecteam) specifically to find *genuine* gaps rather than re-skinning what already matches the category's best-regarded patterns (this app's Check-In screen already had the big-button/GPS-confirmed/card-based look Homebase is praised for).
   - **Staff roster search (added 2026-09-10)**: the Staff tab's roster list is searchable by name, position, or department.

## Profile pictures (added 2026-09-04)

Employees self-service upload their own profile photo (not admin-managed) — shown wherever their identity appears (Staff roster, Staff Attendance rows, Staff Profile, their own Check-In greeting), falling back to initials when none is set. Confirmed with the user this doesn't trigger any KYC/compliance obligation — KYC is a financial-services identity-verification framework tied to regulated money handling, unrelated to a basic profile photo on an internal attendance tool. Stored in a public Supabase Storage bucket (`avatars`) — public read since a profile photo is meant to be seen and is low-sensitivity, unlike attendance coordinates or leave reasons; writes stay fully locked to the account owner. See `ARCHITECTURE.md`'s note on `AppAvatar` and the RLS trigger this needed.

## Employee profile editing (added 2026-09-10)

Admins can edit an employee's name, position, department, and mobile number from that employee's Staff Profile screen — previously nothing but `location_id` was editable anywhere in the app. Deliberately **not** email: that column just mirrors `auth.users.email`, set once at signup; editing it here alone would desync the two (the employee's real login email wouldn't change, so they'd keep signing in with the old address while the app showed a different one). A real email-change flow needs Supabase Auth's own admin API — not built, not needed yet. RLS already permitted this (admins can already update any column on any employee row, `0001`'s `employees_update_admin_only`) — no schema change, just the missing UI.

## Roles (resolved 2026-09-03)
Three app roles: **Employee**, **Admin**, **Super Admin** — simpler than the CRM's 5-role system (`superAdmin`/`admin`/`branchManager`/`pageManager`/`serviceAdvisor`), since this app has no branch/page-manager/service-advisor edit-scoping to replicate. Super Admin is a strict superset of Admin (same pattern as the CRM's own `canEditLead`/`canDelete` in `../crm/src/domain/permissions.ts`) — no separate Super-Admin-only screens exist yet, since nothing Super-Admin-specific has been asked for. Employee *profile* fields (`position`, `department`) are modeled on the CRM's real `employees` table shape (checked directly in `../crm/supabase/wave_2_schema.sql`), since this app tracks the same real staff — but it's this app's own table in its own Supabase project (see Tech Stack), not a live join to the CRM's.

## Open Questions / Not Yet Decided

- **KPI formula** — what actually counts toward performance (on-time %, task count, task difficulty weighting, manual admin scoring, something else). Explicitly deferred by the user until other features are working; needs real input from whoever owns this requirement when it's picked back up.
- **Notifications** — deadlines and geofence auto-checkout both strongly imply push notifications are needed (Expo supports this via `expo-notifications`), but nothing's been decided about what triggers a notification, to whom, or when. Explicitly deferred by the user ("brainstorm later").
- **Location-permission-denial UX** — the geofencing decision above settled the radius/approach, but not what the app should do if an employee denies location permission outright (can they still check in manually with no coordinates recorded? blocked entirely?).

## UX Priority

Explicitly asked to be a first-class concern for this app, not an afterthought — write UI code with the judgment of a professional mobile UX/UI designer (native platform conventions, real loading/error/empty states, accessible touch targets, permission-request flows that explain *why* before asking, not just OS-default prompts with no context). ## Visual Design (resolved 2026-09-04, refined same day)

Airbnb-inspired, on explicit request: their real, publicly documented brand color ("Rausch" coral, `#FF385C`) as the accent, warm neutral surfaces (white/near-white, not cool gray), soft shadow-based cards instead of hard-outlined ones, generous whitespace, and — the part that most directly serves readability, not just looks — their actual text-color pairing (`#222222` primary text / `#717171` secondary text on white), a genuinely well-tested accessible combination, not just borrowed for aesthetics. Typography is **Inter** (not Airbnb's proprietary "Cereal", which can't be legally used) — the open alternative closest in spirit, and specifically designed for screen legibility at UI sizes (same reason GitHub/Figma/Linear use it). See `ARCHITECTURE.md`'s Theming section for the implementation.

**Refined same day** after the first pass "looked quite odd" in practice: bold/semibold had been used for nearly every text role, flattening hierarchy — bold is now reserved for real page-level titles (display/headline) only, everything else is medium at most. Also separated colors by *role*, not just palette: `statusColors.danger` moved off a coral-adjacent red (`#B3261E` now) so a "High priority" flag never reads as the same color as a real coral CTA, static avatars use `secondaryContainer` (teal) instead of `primary` so they don't look like buttons, and buttons that only *display* data (a deadline, an assigned location, a date picker) use neutral `onSurface` text instead of Paper's outlined-button default of `primary`. See `ARCHITECTURE.md`'s Theming section, "Color roles, not just a palette."
